# Warzone Towers 0.29 — optional rewarded ads

Home and in-game Rewards offer an optional **Watch an ad · +10 crystals**
action. The Android Google Mobile Ads SDK reports when the reward has been
earned. Only that native event requests a fixed ten-crystal grant. Opening,
loading, failing to show or dismissing an unearned ad does not grant crystals.
The ordinary game and reward shop remain available without watching ads.

One presentation identity is saved before showing. Crediting ten crystals and
clearing that identity share the wallet's atomic persistent transaction. Old,
cancelled and duplicate callbacks cannot pay twice. A failed write keeps the
same earned identity retryable; it must be saved before another ad is shown.
Existing balances, inventory, prices, native building costs, waves and saved
match identities remain intact. No additional starter gift is introduced.

Consent is handled through Google's User Messaging Platform. Required privacy
choices are available again from Rewards. Fullscreen ad and consent flows hold
the current game document and suspend music, then restore the same document
when the fullscreen activity ends. The existing supported native Escape
pause/resume path is covered by a black Android overlay before input is sent,
so its stock options panel is never exposed to the player. Ordinary header
and gameplay input remain unchanged outside this fullscreen flow.

The pinned Android dependencies are Google Mobile Ads **25.5.0** and UMP
**4.0.0**. Ordinary development builds use Google's official sample IDs.
The delivery build enables the supplied production IDs with
`assembleDebug -PadmobLiveAds=true`. It retains the existing debug signing
certificate so it can update the installed Warzone Towers package and preserve
its private wallet, saves and designs. A production Play Store signing/upload
workflow is separate from this direct-install APK.
On an Android emulator, the controller explicitly requests Google's official
sample rewarded unit even when the APK contains the production IDs. Physical
devices use the configured production unit in the live-ID delivery build.

Live ad serving is external to the APK: the supplied AdMob screenshot shows
account approval and app-store linking still pending. AdMob app verification,
app readiness, the publisher's privacy policy/message configuration and an
`app-ads.txt` file on the developer website must be completed where required.
The implementation does not claim that production ad fill or approval has been
verified. See [AdMob setup](../admob-setup.md).
No publisher consent message was configured externally during this delivery;
UMP did not return a publisher form during the focused emulator observations.
Existing consent choices are not reset or overridden for the test. Publisher
message setup and actual required-form coverage remain external follow-up.

Verification is deliberately bounded. The actual wallet classes run in JVM
fixtures with simulated Android preference I/O: 200 earlier regressions plus
41 focused ad-wallet checks. SDK lifecycle fixtures, when included in the
source reports, simulate callback sequences; they are not real ad views.
Only observations recorded in `qa/0.29-ads/focused-emulator-proof.json` establish
the exact delivery APK's actual screen/ad/lifecycle behavior. Emulator traffic
uses Google's test ads/test-device recognition, never manually tested live ads.
No full campaign, all-map pass, physical-device rendering or live ad revenue
is claimed by these focused checks.

The complete v0.28 APK/source/checksums remain frozen in
`archive/fallback-0.29.json` and the GitHub `v0.28-benchmark` release. Native
engine JS/data/WASM, all 46 maps, map/music assets and the deferred Duel payload
are preserved byte-for-byte. VPS content and older fallbacks remain unchanged.
The intended output files are `Warzone-Towers-0.29.apk`,
`warzone-towers-0.29-source.zip` and `Warzone-Towers-0.29-SHA256.txt`.
